# Sub-Agents

## Overview

Sub-agents allow the Aegis Agent to decompose complex tasks into parallel workstreams by spawning one or more specialized child agents. Rather than tackling every step sequentially, the orchestrator agent can delegate subtasks to sub-agents that run concurrently, dramatically reducing end-to-end task time for multi-step workflows.

Sub-agents are fully managed — you don't configure or deploy them manually. The orchestrator decides when to spawn them, what instructions to give them, and when to aggregate their results.

---

## How Sub-Agent Spawning Works

When the orchestrator determines that a task benefits from parallelization, it:

1. **Decomposes the task** into independent subtasks (e.g., "research competitor A", "research competitor B", "summarize findings")
2. **Spawns sub-agents** for each subtask with scoped instructions and tool access
3. **Runs sub-agents in parallel** — each sub-agent executes independently on its assigned subtask
4. **Aggregates results** once all sub-agents complete (or time out), then synthesizes a final response

Sub-agents inherit a subset of the parent agent's tool permissions. They do not have access to tools outside their assigned scope, and they cannot spawn further sub-agents (only the top-level orchestrator can spawn).

### Example Workflow

> **User prompt:** "Research the top three CRM platforms for a 50-person SaaS company and produce a comparison table."

The orchestrator may spawn three sub-agents simultaneously:

- Sub-agent 1 → researches Platform A
- Sub-agent 2 → researches Platform B
- Sub-agent 3 → researches Platform C

Each sub-agent performs its own web searches and data gathering. The orchestrator waits for all three, then synthesizes the comparison table. Total time: roughly the time of the slowest individual research task, not the sum.

## The Sub-Agent Panel

The **Sub-Agent Panel** is visible in Chat Mode when one or more sub-agents are active. It appears as a collapsible side panel or inline section within the conversation thread, depending on your layout.

### Panel Contents

For each active or completed sub-agent, the panel shows:

| Field | Description |
|---|---|
| **Name / Label** | A short label generated by the orchestrator describing the sub-agent's task |
| **Status** | Running, Awaiting approval, Completed, or Failed |
| **Progress** | A real-time activity indicator showing the sub-agent's current step |
| **Tool Calls** | Count of tool invocations made by this sub-agent so far |
| **Duration** | Time elapsed since the sub-agent was spawned |

Clicking on a sub-agent row expands a detail view showing its full message thread, including tool call cards for every action it took. This gives you complete transparency into how each subtask was handled.

### Real-Time Orchestration View

While sub-agents are running, the orchestrator's status line in the main chat thread updates in real time:

```
Orchestrator: Waiting for 3 sub-agents (2 running, 1 complete)...
```

Once all sub-agents finish, the orchestrator posts its synthesized result to the main thread. The sub-agent panel collapses but remains accessible for review.

## Human-in-the-Loop (HITL) Approvals for Sub-Agents

Sub-agents are subject to the same Tool Permission rules as the orchestrator. When a sub-agent attempts an action that requires approval (e.g., sending an email, writing to a database, or calling a high-risk API), it will pause and surface an **approval card** in the main chat thread rather than failing silently or proceeding without consent.

### Approval Card Behavior

When a sub-agent requires approval, you will see a card in the main conversation thread like:

```
Sub-agent "Outreach Draft" is requesting approval:
  Action: Send email via Gmail
  To: prospect@example.com
  Subject: "Partnership Opportunity"

  [Approve]  [Reject]  [View Details]
```

Key behaviors:

- The sub-agent **pauses execution** and waits for your response
- Other sub-agents **continue running** — only the paused sub-agent is blocked
- If you click **View Details**, an expanded view shows the full action payload (e.g., the complete email body) before you approve
- If you **Reject**, the sub-agent receives a rejection notice and may attempt an alternative approach depending on its instructions
- Unanswered approval requests time out after a configurable period (default: 10 minutes), at which point the sub-agent is cancelled

### Configuring HITL Scope

Whether a sub-agent's actions require approval depends on the tool permission settings configured for the parent agent. Tools set to **"Approve" mode** will always surface an approval card before executing. Tools set to **"Auto" mode** will allow the sub-agent to proceed without interruption. See [Tool Permissions](./tool-permissions.md) for full details.

## Sub-Agent Limits and Plan Availability

| Plan | Max Concurrent Sub-Agents |
|---|---|
| Free | Not available |
| Starter | 2 |
| Pro | 5 |
| Enterprise | Configurable (up to 20) |

When the concurrent sub-agent limit is reached, additional subtasks are queued and started as slots become available. The orchestrator handles this automatically.

Sub-agent runs count against your message/execution quota the same as regular agent turns.

---

## When Sub-Agents Are Not Used

The orchestrator does not always spawn sub-agents. It uses sub-agents only when:

- The task is clearly decomposable into independent parallel subtasks
- Spawning sub-agents would provide a meaningful time or quality benefit
- The task complexity justifies the overhead

For simple, single-step requests, the orchestrator handles the task directly without spawning any sub-agents.

---

## Inspecting Sub-Agent History

After a task completes, the full sub-agent thread history is preserved and accessible via the Sub-Agent Panel. You can:

- Review every message, tool call, and result for each sub-agent
- Export the sub-agent thread for logging or auditing purposes
- Re-run a specific subtask by using its output as context in a follow-up message

Sub-agent history is retained for the same duration as regular conversation history under your plan's data retention policy.
